# Test Mode

Use this mode to run human-like platform testing with a self-healing fix loop. The pipeline scans the codebase, generates test cases, executes them via browser automation, files issues for failures, analyzes root causes, fixes code, and retests — looping until all cases pass.

## Pipeline

| Step | Agent | Produces | Gate |
|------|-------|----------|------|
| 1. Scan & Requirements | [[fury]] | `test-cases/<suite>-requirements.md` | Requirements cover all FRs + rules |
| 2. Test Case Design | [[shuri]] | `test-cases/<suite>.md` | Every requirement has at least one test case |
| 3. Execute | [[widow]] | GitHub Issues for failures | All cases executed with evidence |
| 4. Analyze | [[strange]] | Root cause comments on issues | Every issue has a traced root cause |
| 5. Fix | [[stark]] | Code commits with `closes #N` | TSC clean, fix committed |
| 6. Retest | [[widow]] | Closed issues / new issues | All cases re-executed |
| 7. Loop | — | — | 0 open issues OR max rounds reached |

## Coordination Layer: GitHub Issues

**No agent waits for another agent. Ever.**

State is persisted in GitHub Issues, not in-memory. Each agent:
1. Reads the current state (files, issues)
2. Does its work
3. Writes output (files, issue comments, code commits)
4. Exits

If any agent dies or is interrupted, the state is preserved. The next agent picks up where the pipeline left off.

### Issue Labels

| Label | Meaning |
|-------|---------|
| `widow-found` | Bug discovered by Widow during test execution |
| `strange-analyzed` | Root cause traced by Strange |
| `stark-fixed` | Code fix committed by Stark, pending retest |
| `severity-P0` | Data loss, corruption, or security issue |
| `severity-P1` | Broken workflow — user cannot complete a task |
| `severity-P2` | UX issue — task completable but experience is degraded |

Create these labels before the first run:
```bash
gh label create widow-found -c d73a4a -d "Bug found by Widow automated testing" --force
gh label create strange-analyzed -c 0075ca -d "Root cause analyzed by Strange" --force
gh label create stark-fixed -c 0e8a16 -d "Fixed by Stark, pending retest" --force
gh label create severity-P0 -c b60205 -d "Data loss or corruption" --force
gh label create severity-P1 -c d93f0b -d "Broken workflow" --force
gh label create severity-P2 -c fbca04 -d "UX issue" --force
```

## Deadlock Prevention

The pipeline is **strictly sequential**. No parallel agent execution. No inter-agent messaging. Each step completes fully before the next begins.

Deadlocks are impossible because:
- Agents never wait on each other's responses
- All shared state is in persistent storage (files + GitHub Issues)
- The orchestrator drives the sequence, not the agents

## Gates

- **Requirements gate**: Fury's requirements document references actual code paths, actual rules from project instructions, and actual PRD acceptance criteria. No theoretical requirements.
- **Test case gate**: Every Shuri test case has: navigate steps with real URLs, fill/click steps with role-based selectors, verify steps with expected outcomes. No vague assertions.
- **Execution gate**: Widow has executed every case. Failures have GitHub Issues with reproduction steps and screenshots.
- **Analysis gate**: Every `widow-found` issue has a `strange-analyzed` comment with file:line root cause.
- **Fix gate**: Every `strange-analyzed` issue has a code commit. TSC clean. Commit message references issue number.
- **Retest gate**: Widow has re-run ALL cases (not just previously failed ones). Fixed issues closed. New regressions filed as new issues.

## Loop Termination

- **Success**: 0 open `widow-found` issues after a retest round
- **Max rounds**: 5 fix-retest cycles. If issues remain after 5 rounds, the pipeline stops and lists remaining issues for manual intervention.
- **Escalation**: Issues that survive 3+ rounds are escalated with label `needs-human`

## File Structure

```
.becky/test-cases/
├── seed.md                       ← auth setup for the project
├── <suite>-requirements.md       ← generated by Fury
├── <suite>.md                    ← generated by Shuri, executed by Widow
└── README.md                     ← this documentation

.becky/test-evidence/
├── TC-<suite>-<id>-fail.png      ← failure screenshots
└── ...
```

## Invoking

```
/becky-test <suite-name>
```

If no suite exists, the pipeline starts from Step 1 (Fury scans the codebase and generates requirements). If test cases already exist, the pipeline skips to Step 3 (Widow executes).

To force a full regeneration:
```
/becky-test <suite-name> --fresh
```
