# Becky Test Framework

## Quick Start

```bash
# 1. Copy the Claude Code agents to your project
cp -r .becky-source/agents/claude-code/ .claude/agents/

# 2. Create your seed file
cp .becky-source/templates/test-cases/seed.template.md .becky/test-cases/seed.md
# Edit seed.md with your project's auth setup

# 3. Create GitHub labels
gh label create widow-found -c d73a4a -d "Bug found by Widow" --force
gh label create strange-analyzed -c 0075ca -d "Root cause analyzed" --force
gh label create stark-fixed -c 0e8a16 -d "Fixed, pending retest" --force
gh label create severity-P0 -c b60205 -d "Data loss or corruption" --force
gh label create severity-P1 -c d93f0b -d "Broken workflow" --force
gh label create severity-P2 -c fbca04 -d "UX issue" --force

# 4. Run the pipeline
/becky-test <suite-name>
```

## Pipeline

```
FURY (Scan)      → Reads codebase, rules, PRDs → test requirements
SHURI (Design)   → Converts requirements → step-by-step test cases
WIDOW (Execute)  → Runs tests via Playwright → creates GH Issues for failures
STRANGE (Analyze)→ Traces root cause → adds comments to issues
STARK (Fix)      → Reads issues → fixes code → commits with closes #N
WIDOW (Retest)   → Re-runs ALL cases → closes fixed → opens new
LOOP             → Until 0 open issues (max 5 rounds)
```

## How It Works

### No Deadlocks
Every agent runs sequentially. No agent waits for another. All state is persisted in:
- **Files** — requirements, test cases, evidence
- **GitHub Issues** — failures, analysis, fixes

If any agent dies, the state survives. The next run picks up where it left off.

### Self-Healing
The pipeline doesn't just find bugs — it fixes them:
1. Widow finds a bug → creates an issue with reproduction steps
2. Strange traces the root cause → comments on the issue
3. Stark fixes the code → commits referencing the issue
4. Widow retests → closes the issue if fixed

### Domain-Aware
Fury reads your project's rules (CLAUDE.md, PRDs, conventions) before generating requirements. This means test cases validate business logic, not just "does the button click." The agents know what "correct" looks like because they've read your specs.

## Directory Structure

```
.becky/test-cases/
├── seed.md                       ← auth setup (you create this)
├── <suite>-requirements.md       ← auto-generated by Fury
├── <suite>.md                    ← auto-generated by Shuri
└── README.md

.becky/test-evidence/
├── TC-<id>-fail.png              ← failure screenshots (auto-captured)
└── ...

.claude/agents/
├── fury-test-planner.md          ← scans codebase, writes requirements
├── shuri-test-writer.md          ← writes executable test cases
├── widow-tester.md               ← executes tests, creates GH issues
├── strange-analyzer.md           ← root cause analysis
└── stark-fixer.md                ← fixes code, commits
```

## Writing Custom Test Suites

You can write test cases by hand if you prefer. Follow this format:

```markdown
# Test Suite: <Name>

## TC-<SUITE>-001: <Descriptive Name>
**Priority:** P0
**Covers:** <what requirement or rule>

### Steps
1. NAVIGATE to `/path`
2. VERIFY: <expected state>
3. FILL <field>: `<value>`
4. CLICK button "<label>"
5. WAIT for <condition> (max 10s)
6. VERIFY: <expected outcome>

### Expected Outcome
- <assertions>

### On Failure
Create GH Issue with label: severity-P0
```

## Severity Guide

| Level | Meaning | Examples |
|-------|---------|---------|
| P0 | Data loss, corruption, security | Record saved but total not updated; auth bypass |
| P1 | Broken workflow | User cannot complete checkout; form submission fails |
| P2 | UX degradation | Wrong text shown; layout broken; slow load |
